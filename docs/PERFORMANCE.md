# Бюджет производительности

Все величины МБ/с ниже — десятичные байты/с; МиБ — 2²⁰ байт. Расчёт относится к XC7Z020, DDR 512 МиБ ×16 по [аудиту](zynq7020/BOARD.md). Частота DDR, CPU и реально доступная полоса ещё не измерены.

## Вход, AXI и DMA

| Участок | Требуется | Расчётный предел / допущение | Проверка |
|---|---:|---|---|
| Ветвь AD9288-100 | 100 MSPS × 1 байт = 100 МБ/с | Четыре ветви; всего 400 МБ/с постоянно | Генератор и сравнение порядка A/B, фаз, setup/hold |
| Один аналоговый канал | 200 MSPS, 200 МБ/с | A/B объединяются в PL; нет расширения до uint16/uint32 | Идентифицируемый тестовый шаблон |
| AXI Stream | 400 МБ/с | 64 бит × 100 МГц = 800 МБ/с; загрузка 50%. 64 бит × 150 МГц = 1200 МБ/с — альтернативная частота, не подтверждённая timing closure | RTL stalls, Vivado timing, счётчик принятых байтов |
| HP для capture | 400 МБ/с | Предварительно HP0, 64 бит, 100 МГц. Условные 65–80% эффективности дают 520–640 МБ/с; это плановый диапазон, не измерение | PL test pattern → DDR, затем HDMI и CPU одновременно |
| Альтернатива HP | 200 МБ/с на канал | Два DMA на HP0/HP2 могут улучшить арбитраж; общая DDR остаётся той же ×16 | Сравнить один и два потока на одной DDR |

30% запаса требует **520 МБ/с полезной полосы** для raw capture. 64-bit AXI 100 МГц даёт такой запас лишь при полезной эффективности ≥65%. Если измерение ниже — повысить допустимую частоту, улучшить bursts/арбитраж или проверить разделение потоков; нельзя объявить запас по одной частоте AXI.

Выбран AXI DMA S2MM Scatter-Gather: большие записи в DDR, dmaengine в Linux, аппаратные descriptors и пакетные уведомления. DataMover оправдан при собственном PL-контроллере адресов и записи по триггеру; сейчас его сложность не требуется. GP0 — управление, HP0 — предварительный захват, HP2 — предварительное видео. HP1/HP3 — варианты измерений, а не четыре независимые DDR.

Группа 32 бита за такт 100 МГц содержит CH1_A, CH2_A, CH1_B, CH2_B; две группы упаковываются в AXI beat 64 бит. Отдельные метаданные не расширяют каждую выборку. Для 2 МиБ блока TLAST каждые 262144 beat; 400 МБ/с дают 190,7 блоков/с. Уведомления раз в 4 блока — около 47,7/с с задержкой до 20,97 мс. Финальную настройку выбирать по latency/overruns, не только по числу IRQ.

Software API допускает до 128 блоков: при 2 МиБ это 256 МиБ raw. Лимит не выделяет память и не утверждает доступность такого CMA на плате; размер реального DMA ring задаёт драйвер после проверки RAM. Demo и benchmark используют только 8 блоков. При увеличении записи TLAST/размер SG буфера и notifications согласуются явно.

FIFO выбирается по максимальному времени, на которое DDR может не принимать поток: `size ≥ 400e6 × stall_seconds`. 16 КиБ покрывают 40,96 мкс, 64 КиБ — 163,84 мкс. С запасом 30% для 100 мкс нужно 52 000 байт; округлённо 64 КиБ. Это предварительный бюджет, не гарантированный stall bound. CDC FIFO, setup/hold и запас BRAM проверяются после полного Vivado design. Физический ADC не приостанавливается сигналом TREADY: переполнение FIFO должно давать счётчик, discontinuity и ошибку записи.

## DDR и видео

Для ×16 DDR: `B_peak = clock × 2 transfers × 2 bytes`. Сценарии 400/533 МГц дают 1600/2132 МБ/с теоретически. Частоты не установлены схемой. Для планирования 55–75% полезной эффективности дают соответственно 880–1200 и 1173–1599 МБ/с; это чувствительность расчёта к неизвестной эффективности, не прогноз испытанной платы.

Один кадр `1024 × 600 × 4 = 2 457 600` байт. Два scanout-буфера — 4 915 200 байт (4,6875 МиБ), три — 7 372 800 (7,03125 МиБ). В приложении есть ещё собственный кадр 2,34375 МиБ.

| DDR-трафик при 60 FPS | МБ/с |
|---|---:|
| Запись АЦП DMA | 400 |
| Чтение scanout | 147,456 |
| CPU рисует полный кадр | 147,456 |
| Копирование app frame → scanout, чтение + запись | 294,912 |
| Итого без чтения raw CPU | **989,824** |
| Один полный проход CPU по потоку raw | +400 |
| Итого с одним проходом | **1389,824** |

Для первого сценария 30% запаса — 1286,771 МБ/с; для второго — 1806,771 МБ/с. Уже второй сценарий требует ~84,75% от DDR ×16 @533 МГц, без прочих Linux операций. Текущий ARM processor считает статистику, пересечения и min/max отдельными проходами; при обработке всего непрерывного raw потока верхний бюджет чтений ещё выше. Поэтому **постоянную обработку каждого raw блока ARM не выбираем как обязательный режим устройства**.

Полный raw поток сохраняется DMA в кольце. Для живого экрана PL должен параллельно выдавать min/max buckets и необходимые статистики; ARM обрабатывает ограниченные окна/отдельные записи для FFT и подробных измерений. Прореживание display-потока не заменяет raw capture. Прямой DRM использует два dumb buffer и CPU-копирование; переход к отрисовке прямо в свободный scanout-buffer может убрать 294,912 МБ/с копирования, но требует адаптации stride/владения и измерения. SDL texture/backend может добавлять копирования; их нельзя считать бесплатными.

## Глубина и непрерывный режим

`duration = capture_bytes / 400e6`, число отсчётов на канал `capture_bytes / 2`.

| Raw память | Время при 400 МБ/с | Отсчётов на канал |
|---:|---:|---:|
| 16 МиБ | 41,94 мс | 8 388 608 |
| 64 МиБ | 167,77 мс | 33 554 432 |
| 128 МиБ | 335,54 мс | 67 108 864 |
| 256 МиБ | 671,09 мс | 134 217 728 |

Максимум из всех 512 МиБ был бы 1,342 с, но Linux, видеобуферы, CPU heap/cache и DMA metadata занимают память. Пример бюджета: 192 МиБ Linux+приложение, 32 МиБ видео/запас, 32 МиБ служебная память оставляют 256 МиБ для захвата. Это предложение для измерения RSS/CMA, не фактическое потребление. Pre/post trigger делят выбранный объём; 50/50 у 256 МиБ даёт около 335,5 мс до и после фронта. Не закреплять CMA=256M до проверки реально доступной памяти.

Бесконечный поток не помещается в DDR. Режимы: stop on full для конечной записи; overwrite oldest READY для непрерывного просмотра; drop new с явным счётчиком при отсутствии свободного блока. CPU-owned READING никогда не перезаписывается. Для аппаратного pretrigger нужен кольцевой PL/driver writer с фиксацией trigger sample и остановкой после posttrigger; переносимое кольцо само аппаратный триггер не реализует.

## SD и CPU

SDIO 4-bit × 50 МГц = 25 МБ/с теоретически, 25 МГц = 12,5 МБ/с; фактическая частота и скорость карты неизвестны. Даже теоретические 25 МБ/с в 16 раз меньше 400 МБ/с. Запись 256 МиБ при 25 МБ/с заняла бы не менее 10,74 с, на практике больше. SD — отдельные записи/экспорт и прореженный поток, а не непрерывное raw-хранилище.

Два Cortex-A9 делят обработку/GUI через планировщик Linux; affinity и real-time priority до профилирования не задаются. FFT ограничен 1024 последовательными raw отсчётами с окном Ханна; sample picking через весь захват для FFT не используется из-за aliasing. Для широких окон min/max проходит все отсчёты выбранного окна; measurement/FFT/display rate отличаются от acquisition rate.

## Что измерять

`scope_benchmark 100|200|400|500 seconds` — стенд **на ПК**, с producer/processor/render в отдельных потоках, 8 × 1 МиБ. Отчёт: полезная публикация/обработка, overwrite/drop, peak occupancy, повреждение, render/processing time, cadence GUI и CPU time. Перезаписанные блоки считаются потерянными для processor, даже если producer не остановился.

На Zynq повторить тесты PL→DDR на HP0 и HP2 отдельно/вместе, затем HDMI 60 Hz, затем CPU/экспорт; длительный soak, latency UI, FIFO high water, SG gaps, cache coherency, DMA occupancy. Источник должен реально записывать PL test pattern через DMA. Результаты текущего сеанса и ограничения — [TESTING.md](TESTING.md).
