# Техническое задание для Codex: перенос GUI осциллографа на Zynq-7020 с Linux и подготовка высокоскоростной архитектуры захвата

## 1. Основная задача

Необходимо адаптировать существующее приложение осциллографа для работы на **Xilinx Zynq-7020 под полноценным Embedded Linux**.

Приложение уже написано на C и работает на Windows через WinAPI и на Linux через SDL2.

Нельзя переписывать GUI с нуля или менять его графическую архитектуру без технической необходимости.

Нужно получить автономное устройство, которое:

- Загружает Linux из внутренней памяти платы.
- Автоматически запускает GUI осциллографа.
- Выводит изображение на HDMI-дисплей.
- Принимает мультитач напрямую через USB.
- Обменивается командами с STM32 через UART.
- В будущем принимает высокоскоростные данные АЦП через программируемую логику FPGA.
- Хранит пользовательские данные на съёмной microSD.

**Ключевое требование:** архитектуру передачи данных АЦП, управления памятью и взаимодействия с GUI необходимо спроектировать сразу под максимальную целевую производительность, чтобы последующее подключение реального захвата не потребовало фундаментальной переработки приложения или архитектуры PS/PL.

Продумай безопасное обновление прошивки и восстановление после неудачной загрузки в пределах доступного объёма Flash.

### Важное требование по пропускной способности

Видео должно учитываться при расчёте общей загрузки DDR и AXI.

Для framebuffer ARGB8888 размером 1024×600:

- Один кадр: 2 457 600 байт.
- 60 кадров/с: 147 456 000 байт/с при одном полном чтении кадра.

Это только ориентир на видеочтение без дополнительных копирований, служебных данных и накладных расходов.

Необходимо учитывать, что реальный видеотракт может одновременно читать framebuffer из DDR, а CPU — формировать и копировать новые изображения.

Рассмотри двойную и тройную буферизацию.

Оцени конкуренцию HDMI с DMA-захватом АЦП.

## 8. Высокоскоростной захват АЦП

Это один из важнейших разделов проекта.

Требуется сразу рассчитать архитектуру под максимальную целевую производительность.

### Исходные параметры

Планируется два аналоговых канала.

Для каждого канала:

- АЦП AD9288.
- Две параллельные выборочные ветви A/B.
- По 100 MSPS на ветвь.
- Эффективная частота после интерливинга — 200 MSPS.
- Разрядность выборок — 8 бит.

Общая целевая производительность:

- CH1: 200 MSPS × 8 бит = 200 МБ/с.
- CH2: 200 MSPS × 8 бит = 200 МБ/с.
- Суммарно: 400 МБ/с.

Это исходный поток без расширения выборок до 16/32 бит и без служебных данных.

Проверь параметры конкретной модификации AD9288 по datasheet и сопоставь их с используемой схемой.

### Важнейшее требование

**Не проектируй архитектуру, рассчитанную только на передачу 1024 точек для экрана.**

Экран отображает 1024 точки по горизонтали, но система захвата должна иметь возможность сохранять и обрабатывать значительно больше исходных выборок.

Раздели:

1. Acquisition sample rate.
2. Объём записи.
3. Скорость передачи данных.
4. Скорость обработки.
5. Display refresh rate.

Частота 60 FPS относится исключительно к экрану.

Она не должна ограничивать скорость захвата АЦП.

## 9. PL: сбор данных и интерливинг

Предусмотри следующую концепцию:

AD9288 → Input Capture → Interleaving/Reordering → FIFO → AXI Stream → DMA → DDR.

Для каждого канала обеспечить корректное объединение выборок A/B.

Проверить:

- Тактовые домены.
- Временные ограничения.
- Setup/Hold.
- Порядок выборок.
- Синхронизацию.
- Возможность коррекции временного рассогласования.
- Возможность коррекции gain/offset mismatch.
- Переполнение FIFO.
- Сбои синхронизации.

Определи, где рациональнее выполнять interleaving: непосредственно в PL до DMA или при последующей обработке.

Основной критерий — высокая пропускная способность и минимальная дополнительная нагрузка на CPU и DDR.

При проектировании предусмотри возможность дальнейшего увеличения числа каналов, но не резервируй неподтверждённые аппаратные ресурсы и не обещай сохранения полной скорости без расчёта.

Рассмотри:

- AXI4-Stream.
- AXI DMA.

- AXI HP0/HP1/HP2/HP3.
- AXI GP для управляющих регистров.
- Возможность использования нескольких DMA-каналов.

- Scatter-Gather DMA.
- Циклические DMA-буферы.
- Прерывания и пакетное уведомление о завершении передачи.

Не выбирать порты и конфигурацию DMA только по теоретической пиковой скорости.

Для выбранной аппаратной платформы рассчитай:

1. Скорость данных от каждого АЦП.
2. Пиковую и среднюю нагрузку на входы PL.
3. Ширину внутренних потоков данных.
4. Частоту тактирования AXI Stream.
5. Пропускную способность DMA.
6. Пропускную способность выбранных HP-портов.
7. Пропускную способность DDR.
8. Дополнительный DDR-трафик от видеоконтроллера.
9. Дополнительный DDR-трафик от CPU.
10. Потери на арбитраж, burst overhead и ожидания.
11. Необходимую глубину FIFO.
12. Размер буферов захвата.
13. Предельную продолжительность записи в зависимости от объёма DDR.
14. Поведение при длительном непрерывном захвате.
15. Влияние записи данных на SD-карту.

Отдельно оцени сценарий, когда оба канала непрерывно передают 400 МБ/с, HDMI одновременно выводит изображение, а Linux выполняет обработку и пользовательские операции.

Учти, что HDМI, AXI и DDR могут иметь общие ресурсы и конкурировать за доступ к памяти.

Для каждого участка укажи:

- Теоретический предел.
- Ожидаемый практически достижимый диапазон.
- Необходимый запас.
- Узкое место.
- Способ проверки на реальном железе.

Все оценки должны иметь явные допущения. Не выдавай теоретическую пропускную способность AXI за измеренную.

### Целевой запас

Стремись к запасу производительности не менее 30% относительно требуемого среднего потока там, где это аппаратно возможно.

Если обеспечить такой запас невозможно, укажи ограничения и предложи архитектурные решения.

Не увеличивай разрядность хранимых выборок с 8 до 16/32 бит без обоснования, поскольку это увеличит трафик DDR.

## 11. Управление буферами захвата

Необходимо спроектировать высокопроизводительный интерфейс передачи больших блоков выборок.

Предусмотреть:

- DMA ring buffer.
- Несколько независимых буферов.
- Выравнивание памяти.
- Разделение владения буферами между DMA и CPU.
- Управление cache coherency.
- Счётчики потерянных блоков.
- Обработку ошибок.
- Аппаратные и программные временные метки.
- Возможность записи до и после триггера.
- Передачу метаданных захвата.
- Безопасную публикацию заполненных буферов пользователю.

Приоритет — отсутствие лишнего копирования многосотмегабайтных потоков.

Рассмотри zero-copy там, где он действительно реализуем и безопасен.

Не используй обычный `malloc()` как единственный механизм организации DMA-памяти.

### Разделение ответственности

FPGA отвечает за высокоскоростной сбор и первичную буферизацию.

DMA отвечает за перемещение данных в DDR.

Acquisition Worker отвечает за управление буферами и получение завершённых блоков.

Processing Worker отвечает за подготовку данных для отображения и измерений.

GUI отвечает только за визуализацию и пользовательское управление.

Медленный GUI не должен блокировать аппаратный захват.

Определи политику при заполнении памяти: остановка захвата, перезапись старейших данных или потеря непрочитанных блоков. Для каждого режима явно описать поведение.

При этом обработка, буферизация и интерфейсы должны быть пригодны для будущего аппаратного источника.

### Обработка

Предусмотреть:

- Преобразование кодов АЦП в физические величины.
- Калибровку.
- Вертикальное масштабирование.
- Горизонтальное масштабирование.
- Decimation.
- Min/Max aggregation.
- Подготовку отображаемых 1024 точек.
- FFT.
- Измерения.
- Курсоры.
- Отображение записанной осциллограммы.
- Возможность изменения масштаба после остановки захвата без потери исходных данных.

Для сильного уменьшения временного масштаба использовать методы, сохраняющие короткие импульсы и выбросы, а не просто выбирать каждую N-ю выборку.

Проверь, где лучше делать decimation — в PL или ARM, чтобы уменьшить нагрузку на DDR и CPU, не теряя возможность сохранения полных данных.

Отображаемые данные должны обновляться независимо от приёма новых блоков.

## 7. Согласованность версий

Предусмотри версионирование интерфейсов между:

- FPGA и Linux-драйвером.

- STM32 и Zynq.

Рассмотри:

- Версию карты AXI-регистров.
- Версию формата DMA-данных.
- Версию UART-протокола.
- Версию приложения.
- Версию FPGA Bitstream.

Не нужно создавать чрезмерно сложную систему управления версиями.

Достаточно простого, документированного механизма, обеспечивающего воспроизводимость релиза устройства.

## 8. Работа с прошивками и сборочными артефактами

Все проекты должны быть воспроизводимыми из исходников.

Для FPGA предпочтительно использовать Tcl-скрипты Vivado и сохранять исходные RTL, XDC и необходимые конфигурации IP.

Для Embedded Linux сохраняй конфигурации Buildroot, Kernel, Device Tree и необходимые скрипты.

Не добавляй в Git большие автоматически генерируемые каталоги Vivado и Buildroot.

Не храни временные файлы компиляции в исходном репозитории.

Бинарные образы прошивок, Linux и FPGA рассматривай как артефакты конкретных релизов.

Подготовь понятную процедуру сборки всех компонентов устройства.
