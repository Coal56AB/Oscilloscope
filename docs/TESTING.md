# Выполненные проверки

## 23 октября 2026 — масштаб времени в STOP за пределами записи

- Linux CTest **9/9**, Windows MSVC **4/4**. Проверены изменение развёртки
  энкодером, сенсорным API и меню в STOP, сжатие записи вдвое/впятеро,
  пустые области по краям, возврат исходного изображения, неизменность source,
  sequence и временной привязки. ZOOM после сжатия использует правильный шаг.
- Новый тест renderer сравнивает пустые области и внутренний разрыв с фоном
  без канала: ни обычная линия, ни min/max, ни послесвечение не рисуют там
  ложный сигнал. Фильтр не заполняет отсутствующие точки, Vpp не включает
  маркер пропуска. CSV прежнего формата сохраняет пропуски при повторном чтении,
  позволяет сжать сохранённую запись и вернуть исходный вид.
- Raw processor проверен с экранным интервалом шире памяти, частичным столбцом,
  полностью отсутствующим пересечением и невалидными параметрами. Импульс остаётся
  на физическом месте. Потоковый pipeline после STOP меняет отображение без
  новых блоков и без смены sequence. В статистику входят только реальные точки.
- На изображениях настоящего renderer 1024×600 визуально проверены исходная
  запись 100 мкс/дел, сжатие до 500 мкс/дел и горизонтальное перемещение:
  десять периодов занимают пятую часть сетки, за границами запись отсутствует.
  Это программная проверка; на физической плате изменение ещё не испытано.

Изменение затрагивает GUI Zynq/Windows/Linux, исходники STM32 не менялись.
Buildroot собрал ARM GUI и итоговый FIT; `image.bin` и `qspi.bin` обновлены.
Проверены исходники ARM build, вложенный rootfs и побайтное совпадение ELF
из конечного `image.bin` с установленными файлами сборки. BOOT/FIT/QSPI payload
и резервные области прошли `verify_release.py`. BOOT.BIN и FSBL не изменялись;
для обновления достаточно `image.bin` по адресу QSPI `0x520000`.

## 23 октября 2026 — запуск энкодера между щелчками и настоящая K1

- Владелец воспроизвёл мёртвую зону после включения с энкодером между фиксациями.
  Предыдущая привязка к стартовому снимку была недостаточна. Добавленный сценарий
  с физической опорой 11 и стартом в 00 провалился на первом обратном щелчке.
  Теперь `Encoder_Init` получает фазу отдельным параметром; в прошивке задана
  программная опора 11. Тесты проходят для четырёх опор и четырёх начальных
  состояний, обоих направлений доводки/реверса, дребезга и 2/4 переходов на шаг.
  STM32 CTest **6/6** на Windows и Linux. Keil 6.19: HEX/AXF слинкованы,
  **0 ошибок, 0 предупреждений**. Конкретная фаза механических фиксаций на
  установленной детали ещё не измерена; значение 11 — настройка, не измерение.
- Визуально повторно проверены листы 4/5/9 оригинальной схемы: K1 — PS MIO0/E6;
  K2 — PL KEY1/M20; K3 — PL KEY2/M19. Старый код читал M19, что соответствует
  наблюдению владельца о реакции на K3. Новый транспорт K1 выбирает gpiochip с
  label `zynq_gpio` и запрашивает только line 0 как input/active-low. Тест
  подтверждает пропуск PL-контроллера, правильные offset/flags, нажатие/отпускание,
  занятую линию, потерю устройства, закрытие fd и повторное открытие.
- Linux GUI/служба собраны, CTest **9/9**. Интеграционный тест реальной службы и
  SDL GUI прошёл heartbeat, SIGSTOP/TIMEOUT, SIGCONT и штатное завершение.
  В текущем ядре проверены GPIO_ZYNQ, GPIO_CDEV и GPIO_CDEV_V1; последние два
  параметра добавлены явно в kernel.fragment. FPGA/FSBL для исправления K1
  не меняются. Физическое переключение страниц новой прошивкой ещё не испытано.
- Новый транспорт K1 собран отдельно с `-std=c11 -Wall -Wextra -Werror`, тест
  прошёл. Windows GUI собран, CTest **4/4**; проверка структуры CubeMX/Keil
  `check_project.py` — PASS. Buildroot собрал ARM-службу и итоговый FIT;
  в штатной выдаче обновлены BOOT.BIN, image.bin и qspi.bin, сохранён fsbl.elf.
  Проверены BOOT/FIT, размещение payload и резервов QSPI; служба, извлечённая
  из initramfs внутри FIT, побайтно совпадает с установленной ARM-службой.

## 23 октября 2026 — реверс энкодеров и удержание кнопок меню

- Новый `stm32_encoder` воспроизвёл прежнюю ошибку: скачок сразу обеих фаз,
  несколько полных шагов вперёд, затем полный шаг назад без события. С фиксацией
  границы детента к начальной фазе тест проходит. Проверяются четыре начальные
  фазы, оба направления, реверс каждого щелчка, дребезг, частичный поворот с
  возвратом, повреждение на каждом участке цикла и восстановление в обе стороны.
  Режимы 1/2/4 перехода проверены; настройка платы 4 перехода сохранена.
- STM32 host CTest **6/6** на Windows MSVC и Linux GCC. В Keil Arm Compiler
  6.19 полностью слинкован `STM32/output/oscill_controls.hex`: 0 ошибок,
  0 предупреждений. Изменён общий декодер в субмодуле `AllLibs/PeriphGeneral`;
  SCALE/POSITION и физическая карта GPIO этим исправлением не менялись.
- Для CH1, CH2, CURSOR, TRG MODE и MENU/BACK проверено закрытие открытого меню
  удержанием отдельной кнопки, включая незавершённое редактирование триггера.
  SDL frontend проверяет порог и отпускание всех пяти кнопок: после удержания
  нет короткого действия, переключения канала, курсоров, режима триггера или ZOOM.
- DOUBLE CLICK по умолчанию **300 мс**: оба канала выключаются на границе
  300 мс и остаются включёнными при 301 мс. Долгое нажатие очищает последовательность
  двойного клика. Старый сценарий включения ZOOM из открытого меню обновлён:
  первое удержание MENU закрывает меню, следующее включает ZOOM.
- Итоговые GUI CTest: Windows **4/4**, Linux **8/8**. Buildroot пересобрал
  ARM GUI и FIT с этими изменениями и значением 300 мс; в штатной выдаче обновлены
  `BOOT.BIN`, `image.bin`, `qspi.bin`, сохранён соответствующий `fsbl.elf`.
  Проверены заголовки, размеры, резервные области и вложенные payload QSPI;
  исходники сборки совпадают с рабочими файлами, GUI, извлечённый из FIT/initramfs,
  побайтно совпадает с установленным ARM-приложением.
- Проверки электрических последовательностей выполнены через fake GPIO с
  настоящим библиотечным `Encoder_Update`; измерения A/B на панели не проводились.
  В первой версии фаза при инициализации считалась положением фиксации;
  это ограничение устранено в следующей проверке выше. Точное исполнение
  EC11E и число переходов на щелчок требуют проверки установленной детали.

## Программная нагрузка на ПК

Release `scope_benchmark RATE 3`: отдельные producer/processor/render потоки, 8 × 1 МиБ, producer копирует заранее подготовленный шаблон, processor выполняет raw statistics/min-max/FFT, renderer рисует CPU кадр. Память повторно используется и может находиться в cache. Здесь нет PL, DMA, USB или HDMI scanout. Частота захвата в metadata не является фактически выполненным ADC sampling.

|---:|---:|---:|---:|---:|---:|---:|---:|---:|---:|

Средняя отрисовка: 0,461–0,509 мс; максимальная: 0,785–1,052 мс. Максимальный промежуток между началами кадров: 17,588–17,836 мс. Нагрузка 500 МБ/с превышает возможности данного processor на этом ПК; overwrite ожидающих READY учитывается, CPU-owned блоки защищены. Processed rate включает время drain после завершения producer, published rate делится на заданные 3 с. FPS относится к вызовам CPU renderer, не к предъявлению HDMI кадров.

`corrupt=0` во всех четырёх прогонах — выборочная проверка байтов через 4096 байт, а не CRC всего потока. Полный CRC payload проверяется отдельно в файловом тесте. Для измерений DDR/DMA нужен аппаратный PL test pattern с sequence и проверкой полного payload.

## Невыполненные аппаратные и системные проверки

FSBL, HDMI bitstream и полный Linux-комплект собраны. GUI запущен в ARM Linux в QEMU с SD и QSPI. Эмулятор запускает U-Boot ELF напрямую на одном CPU: BootROM/FSBL/PL, реальная DDR, второй CPU, HDMI-разъём и USB3320/HID сенсора этим прогоном не проверяются. USB PHY в модели не отвечает; это не результат проверки USB платы. Tinker ARM32/ARM64 package не пересобирался; source list и shell syntax обновлены.

На устройстве предстоит проверить:

1. DDR handoff, UART console, восстановление и загрузку QSPI без карты.
2. HDMI mode/pixel clock и длительную работу около 60 Hz. Первый Linux-комплект копирует кадры в одну framebuffer-поверхность; page flip относится к отдельному DRM backend.
3. USB Host/VBUS, фактический HID single touch или multitouch, pinch при наличии двух контактов и отсутствие mouse duplicates; reconnect/SYN_DROPPED.
4. Физический UART STM32, последовательности encoder/down/up/hold/chord, повреждения и разрыв связи.
5. DMA PL pattern сначала без видео, затем с HDMI и обработкой: 100/200/400 МБ/с, повышенная нагрузка и soak. Полный контроль payload, FIFO/SG/queue counters и cache coherency.
6. STOP/pretrigger/posttrigger, масштабирование всей сохранённой raw записи, реальную задержку реакции интерфейса.
7. Raw export, SD speed/full/eject/reinsert и сохранность файлов.

До этих проверок нет подтверждения 400 МБ/с на Zynq с HDMI и 20–30% запасом. Расчёт потенциального DDR bottleneck — [PERFORMANCE.md](PERFORMANCE.md), оставшаяся реализация — [DECISIONS.md](DECISIONS.md).

## Масштабирование исходного сигнала

`scope_runtime` проверяет сжатие одиночных импульсов и повторное построение увеличенного участка из того же raw-буфера, включая интерполяцию между исходными отсчётами и неизменность записи. `scope_simulator` проверяет сетку демо-шума на быстрой основной развёртке 500 ns/div, ограничение записи до 8192 отсчётов на канал, уменьшение частоты захвата при увеличении времени основной развёртки, изменение min/max шума между кадрами RUN и неизменность исходного буфера при ZOOM. `scope_rendering` проверяет цветной штрих толщиной 1 px при обычной развёртке и разных высотах окна ZOOM. Эти проверки выполняются на ПК; реальный захват АЦП ими не подтверждается.

## Диагностика UART

После пересборки с `DIAGNOSTICS=0` значение проверено в SquashFS и initramfs. Проверка `verify_release.py` прошла для SD/QSPI образов. В QEMU 6.2 выполнена прямая загрузка ядра, DTB и initramfs: подтверждены работа GUI, отсутствие `--diagnostics` в аргументах процесса и периодических строк `render_ms`/`touch_connected` в UART за шесть секунд наблюдения. Параметр эмулятора `mem=496M` оставляет верхние 16 МиБ для framebuffer, поскольку при прямой загрузке QEMU заменяет размер памяти из DTB. Этот прогон не проверяет загрузку через U-Boot, SD/QSPI и запуск на плате.

## Время загрузки

В конфигурациях удалены паузы U-Boot 2 секунды и запуска GUI 4 секунды; `loglevel=4` сохраняет вывод предупреждений и ошибок ядра в UART. QSPI-команда читает заголовок FIT, получает `totalsize`, проверяет пределы 40…0x9e0000 байт и читает только образ. Для собранного FIT размером 7 112 320 байт это исключает чтение 3 242 368 байт заполнения. Скрипт сборки обновляет Device Tree ядра/U-Boot и `boot.scr` также при повторной сборке.

Buildroot пересобрал ARM GUI, U-Boot и DTB; проверены параметры в U-Boot, DTB и SquashFS, shell syntax, три теста QSPI-layout и `verify_release.py`. В QEMU 6.2 U-Boot загружает Linux с SD и из FIT, GUI автоматически работает с `START_DELAY=0` и без периодической диагностики. Для FIT проверены чтение 40-байтового заголовка, получение длины, отклонение значений меньше заголовка и больше раздела, загрузка через `bootm` с проверкой SHA-256 всех трёх payload. В FIT-прогоне чтение выполняется из эмулированной SD: физический QSPI этим прогоном не проверяется.

Первоначальное наблюдение владельца при загрузке из QSPI: около 4 секунд от FPGA DONE до логотипа и ещё 5–6 секунд до GUI. После удаления программных пауз изображение появляется около `oscill login`; предоставленный UART-журнал содержит `FPGA Done!` и затем `SPLASH_READY` до передачи управления U-Boot, но не содержит временных отметок.

09.10.2026 владелец остановил загрузку на приглашении U-Boot: логотип появился без запуска Linux, примерно через те же 4 секунды. Это подтверждает работу заставки FSBL на плате и исключает необходимость Linux для её появления. Дисплей питается от отдельного источника; при reset платы его питание сохраняется. При отключении и повторном подключении HDMI уже работающего GUI изображение возвращается примерно через 2,5 секунды без reset платы. Дисплей вносит заметную задержку восстановления изображения; время выполнения FSBL и момент начала корректного HDMI-сигнала ещё не измерены. Оценки владельца приблизительные: разность этих двух наблюдений не является измерением времени FSBL.
