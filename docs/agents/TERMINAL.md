# ПК-приложение Oscill Terminal

## Запуск и подключение

Готовое приложение — `TERMINAL/output/OscillTerminal.exe`: самостоятельный Windows x64 EXE. Python и Qt на компьютере пользователя устанавливать не требуется.

1. Подключить USB–UART осциллографа, выбрать COM-порт и скорость Linux-консоли. Для текущей прошивки — 1000000 бод, 8N1, без управления потоком. Приложение запоминает выбранную скорость.
2. Нажать «Подключиться». Приложение запрашивает приглашение Linux и автоматически входит как `root` в штатный образ без пароля. Если задан пароль, открывается вкладка «Терминал» для его ввода. До приглашения shell чтение и управление недоступны. В терминале печатать прямо в консольном окне: Enter отправляет строку; Ctrl+C прерывает команду, Ctrl+V вставляет текст, ↑/↓ выбирают ранее введённые команды. Ответы и приглашение shell появляются в том же окне. Пароль не отображается, когда Linux отключает echo; неотображаемый ввод не попадает в историю приложения.
3. На вкладке «Linux» нажать «Проверить консоль» и «Связь с GUI».
4. На вкладке «Осциллограф» нажать «Считать настройки» или «Считать окно». Поля заполняются фактическими значениями устройства. Изменить параметры и нажать «Применить изменения»; приложение перечитает подтверждённые значения и осциллограмму.
5. Носитель с меткой `OSCILL` или ранее выбранный через «Монтировать SD» подключается автоматически при загрузке и вставке. Для первого выбора другого носителя открыть «Носители», указать фактический раздел и нажать «Монтировать SD». Вкладка «SD-карта» показывает дерево `/media/scope`; папки читаются при раскрытии. Выбранный файл можно скачать на ПК. Перед физическим извлечением карты нажать «Извлечь SD» на вкладке «Linux»; автоматическое монтирование блокируется до следующего ручного монтирования или перезапуска устройства.

Скорость USB–UART выбирается на устройстве в `PC CONNECTION → UART BAUD` и в строке подключения приложения. Доступны значения до 2 000 000 бод. Для изменения скорости отключить ПК-приложение, выбрать скорость на устройстве, затем выбрать такое же значение на ПК и подключиться. Изменение действует до перезапуска устройства; загрузка начинается на 1 000 000 бод. USB–UART доступен постоянно и отдельного режима USB нет. `USB-UART READY` означает доступный UART, `PC ACTIVE` — запросы управления за последние десять секунд.

Вкладка «Прошивка» обновляет Zynq из каталога с `BOOT.BIN` и `image.bin`, проверяет передачу и запись и показывает прогресс. Порядок работы — [UART_UPDATE.md](UART_UPDATE.md).

## Настройка и график

Доступны прямые параметры:

- CH1/CH2: включение, В/дел, DC/AC, щуп ×1/×10, вертикальное смещение и фильтр;
- развёртка: время/дел и горизонтальное смещение;
- триггер: AUTO/NORMAL/SINGLE, CH1/CH2, нарастающий/спадающий/оба фронта, уровень в вольтах и holdoff;
- отдельные кнопки запуска, остановки, одиночного захвата и принудительного запуска.

Диапазоны масштаба и времени считываются из модели устройства. Изменения отправляются как значения параметров. Общий API модели используется также локальными меню; переключать меню на устройстве для настройки с ПК не требуется. При обновлении графика неприменённые значения в полях сохраняются. Настройки недоступны до первого чтения состояния.

«Применить изменения» запоминает значения на момент нажатия, даже во время приёма окна. Они выполняются после текущего обмена с приоритетом перед следующим автоматическим чтением. Повторные нажатия сохраняются в порядке поступления. Правки, сделанные после нажатия, остаются в полях после подтверждения и требуют следующего применения. При отключении незавершённые операции отменяются с сообщением.

График строится на ПК из двух массивов текущего окна по 1024 точки. Время показано относительно триггера; левая шкала напряжения относится к CH1, правая — к CH2. Пересчёт в вольты использует нули и масштабы CSV. Vpp и RMS под графиком рассчитаны по этим экранным точкам. CSV сохраняет последнее считанное окно в прежнем формате устройства. Источник данных `demo`/`raw` отображается рядом с RUN/STOP; ПК-приложение самостоятельно сигнал не генерирует.

«Обновлять график» включает периодическое чтение. Значение 0,5…3600 секунд — пауза после завершения передачи; сама передача занимает дополнительное время. Параллельные чтения не запускаются. Обновление ждёт, если занят общий COM-порт или пользователь ещё не закончил строку в терминале. При отключении периодическое чтение останавливается.

Вкладка «Linux» предоставляет сведения о системе, памяти, процессах, файловых системах, сети, журнале ядра и настройках устройства, а также выполнение неинтерактивных команд с правами вошедшего пользователя. Терминал поддерживает LF, CR и CRLF, управление курсором и очисткой строк ANSI; полноэкранные TUI не реализованы. Время ожидания команды — 60 секунд. При незавершённом автоматическом ответе соединение закрывается; повторное подключение выполняется кнопкой.

## Сборка ПК-приложения

Нужны Python **3.7.9 x64** и Visual Studio 2019 / Build Tools 2019 с C++ toolset **14.2** и Windows SDK. Из корня репозитория:

```powershell
py -3.7 -m venv TERMINAL/output/venv
./TERMINAL/output/venv/Scripts/python.exe -m pip install -r TERMINAL/requirements-build.txt
./TERMINAL/output/venv/Scripts/python.exe TERMINAL/build_and_clean.py
```

Скрипт использует предоставленный способ сборки: Nuitka `--standalone --onefile`, плагин `pyside2`, отключённую консоль Windows. Зафиксирован MSVC 14.2; проверенная версия Nuitka — 2.8.10. Запускается именно интерпретатор сборочного окружения. PyInstaller не требуется. Зависимости закреплены в `requirements*.txt`; соседний BusTerminal не используется.

EXE и отчёт компиляции находятся в `TERMINAL/output/`. После успешной сборки промежуточные каталоги удаляются; для их сохранения есть `--keep-build`.

## Сторона осциллографа

SDL-приложение поддерживает `--remote-socket /run/oscill-control.sock`; штатный `S99oscill` передаёт этот параметр. CMake устанавливает `scope_preview` и клиент `oscill-remote` в `/usr/bin`. Qt на устройство не добавляется. Сборка Linux описана в [BUILD.md](BUILD.md).

Поддержка управления с ПК включена в штатный rootfs внутри `ZYNQ7020/output/linux/image.bin`. При обновлении имеющейся QSPI-системы достаточно записать этот файл с offset `0x520000`: FSBL, bitstream и U-Boot для этой функции не меняются. Способ записи описан в [FLASHING.md](FLASHING.md).

UART-команды используют имеющиеся в BusyBox `sh`, `gzip`, `base64`, `ls`, `dd`, `tr`. SD читается как смонтированная файловая система; работа с сырыми секторами и форматирование не выполняются.

## Модули и протокол

- `transport.py` — serial I/O в отдельном потоке, последовательные запросы и таймауты;
- `protocol.py` — кадрирование shell-ответов и кодирование путей; `capture.py` — разбор окна и пересчёт координат, оба без Qt;
- `session.py` — единственный владелец соединения, текущего и отложенных запросов;
- `*_ui.py` — вкладки, `app_ui.py` — окно, `mainterm.py` — точка входа;
- `remote_control.c` — неблокирующий Unix socket; `remote_client.c` — консольный клиент; frontend связывает запросы с общим API модели.

Socket имеет права 0600. Один клиент отправляет одну строку менее 128 байт, получает `OK длина\n` либо `ERR длина\n` и указанное число байт. Команды: `ping`, `state`, `window`, `csv`, `set KEY VALUE`, `run`, `stop`, `single`, `force`. `state` возвращает JSON с параметрами и поддерживаемыми диапазонами; `window` — строку такого JSON и прежний CSV текущего окна. CSV записывает канонический `wave_file_write`. Изображение экрана по этому интерфейсу не передаётся. `presented_ns` обозначает метку принятия показанной записи, `presented_at_ns` — время её фактического вывода по монотонным часам. Повторное рисование UI с прежней записью это время не меняет. Для аппаратной записи `ch1_frequency_hz` / `ch2_frequency_hz` и `ch1_duty_percent` / `ch2_duty_percent` содержат текущие оценки либо `null`. Чтение `state` не перестраивает график.

Напряжения текущего кадра доступны в `ch1_vpp_volts`, `ch1_minimum_volts`,
`ch1_maximum_volts`, `ch1_mean_volts`, `ch1_rms_volts` и аналогичных полях CH2.
`ch1_raw_mean_volts`/`ch1_raw_rms_volts` и поля CH2 показывают отдельную
исходную статистику калибровки. Для выключенного канала или отсутствующих
отсчётов возвращается `null`; экранный CSV сохраняет прежний формат.

Счётчики `capture_blocks`, `capture_dropped`, `capture_overwritten` и
`source_error` позволяют отличить пропуски входных DMA-блоков от замены
ожидающей обработки записи и ошибки источника. Пропуски определяются по
аппаратным номерам блоков; это не счётчик пропущенных посылок на входе.
`capture_rejected` считает тихие блоки, исключённые по аппаратной сводке
без полной распаковки; они учтены в `capture_blocks`, а не в пропусках.
`capture_probe_blocks` считает блоки, для которых принята совпадающая с
текущим запросом аппаратная проверка LOW/HIGH из MMX3.
`capture_deadtime` считает блоки, принятые во время показа предыдущего захвата
или полностью попадающие в holdoff. Их исходные данные не проверялись на
новый фронт; выбранная запись сохраняется до фактического вывода.
`capture_acquisition_ns` и `capture_search_ns` накапливают время этапов
приёма с копированием истории и поиска по монотонным часам. Приём включает
ожидание DMA; `capture_search_max_ns` — наибольшее время одного поиска.

`set` принимает ключи полей состояния: `ch1_`/`ch2_` + `enabled`, `coupling`, `probe_ten`, `scale_index`, `position`, `filter`; `time_index`, `time_position`; `trigger_mode`, `trigger_source`, `trigger_edge`, `trigger_holdoff`, `trigger_level`. Дискретные значения — индексы существующих вариантов; `position` — пиксели существующей модели, уровень триггера — вольты. Значения проверяются до изменения состояния. Прямое применение не требует открытия меню. Существующие ограничения модели, включая экспериментальный raw pipeline, сохраняются.

Сервер ограничивает отправку по socket за одну итерацию GUI и не блокирует его на медленном клиенте. При запуске не удаляет уже существующий socket. После штатного завершения socket удаляется.

Общий `linux_serial.c` задаёт соответствие скоростей termios для UART-консоли и транспорта органов управления. Скорость существующего tty меняется с сохранением остальных настроек Linux-консоли. SDL получает путь через `--console`, штатный запуск передаёт `/dev/ttyPS0`. Это UART shell ПК; `--serial`/`--baud` относятся к отдельному транспорту органов управления и не меняются. Поля `uart_baud` и `pc_active` добавлены к состоянию remote API.

`oscill-card mount` сохраняет файл `.oscill-data` на выбранной файловой системе. Служба `S98oscill-card` проверяет носители каждые две секунды; метка `OSCILL` и этот файл позволяют найти подготовленный носитель после смены имени устройства и перезапуска. Проверка файла выполняется временным монтированием только для чтения; уже используемые файловые системы пропускаются. Файловая система не форматируется. `unmount` ставит запрет автомонтирования в `/run`, чтобы извлечённая карта не подключалась снова сразу после команды.

Через UART скрипт команды передаётся одной строкой base64. Ответ окружён уникальными строками BEGIN/END; данные и код завершения сжимаются gzip и кодируются base64. ПК проверяет статус команды и gzip CRC. Предел распакованного ответа — 8 МиБ. Служебные ответы не показываются в терминале; его ввод во время автоматического запроса не перемешивается с передачей. История терминала содержит только введённые пользователем команды, показанные Linux через echo. Параметры и график — отдельные запросы; время ожидания окна — 60 секунд, прочих запросов — 30 секунд.

Имена SD кодируются base64, включая пробелы, кавычки и переносы строк. Реальный каталог проверяется относительно выбранного корня после `cd`/`pwd -P`; ссылки показываются без перехода. Файлы читаются блоками 49152 байта, таймаут — 90 секунд на блок. Размер проверяется, локальная запись использует `QSaveFile`: ошибка, отключение или отмена сохраняют прежний файл. Отмена завершается после текущего блока. Изменение содержимого без изменения размера не обнаруживается; каждый ответ защищён gzip CRC.

## Проверки

```powershell
./TERMINAL/output/venv/Scripts/python.exe -m unittest discover -s TERMINAL/tests -p test_protocol.py -v
./TERMINAL/output/venv/Scripts/python.exe -m unittest discover -s TERMINAL/tests -p test_gui.py -v
./TERMINAL/output/venv/Scripts/python.exe TERMINAL/tests/check_standalone.py TERMINAL/output/OscillTerminal.exe
```

На Linux после сборки SDL GUI и ARM GUI:

```sh
python3 TERMINAL/tests/test_device.py --build-dir /absolute/linux-build -v
python3 TERMINAL/tests/test_arm.py --images /absolute/buildroot-images
```

Проверены 6 тестов framing/путей, включая сообщения ядра среди строк ответа, и 6 Qt-тестов: вход в shell, serial I/O и запрет перемешивания, отложенное применение перед следующим опросом и сохранение поздних правок, ожидание окончания строки терминала, единый терминал с клавиатурой/историей, сохранность файла при скачивании. Два интеграционных Linux-теста проверяют настоящий SDL frontend, socket-клиент, все доступные поля настройки, окно/CSV и чтение файлов с необычными именами. Регрессионные CTest — 5/5 Linux и 3/3 Windows, включая длительность уведомлений независимо от числа обновлений захвата, скорость tty и подтверждённый статус UART. ARM-сборка выполнена; команды окна, настройки и SD, автомонтирование по метке и сохранённому выбору на двух холодных запусках проверены в QEMU на ядре/rootfs проекта с его BusyBox.

Самостоятельный EXE проверяется из пустого каталога: только копия приложения, Python вне PATH, неверные PYTHONHOME/PYTHONPATH; создаются и отрисовываются четыре вкладки, приложение завершает тест с кодом 0. На физической плате проверены UART-вход, `ping`, настройки и по 20 окон с проверкой целостности на 115200 и 1 000 000 бод. Медианное время одного запроса в этой проверке — 0,641 и 0,172 секунды; после проверки восстановлено 115200. Аппаратный захват и автомонтирование после перезапуска платы не проверялись.
